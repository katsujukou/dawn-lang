# Design Decisions

Each decision states what Dawn does, why, and how costly it is to revisit. Alternatives that Dawn rejects are recorded with the reason, so that reopening a decision starts from the argument rather than from scratch.

Reversibility is graded **low** (the decision is load-bearing; changing it propagates widely), **medium**, or **high** (local, or surface-only).

## Calculus and kinds

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D1 | The Core calculus is **System F extended with kinds, higher-kinded type variables, rows, and effect rows**. It has no type-level lambda, so it is a subsystem of System Fω rather than Fω itself. It does not adopt System FC coercions | Without type-level functions, type equality is syntactic apart from row normalization. Type constructors can be abstracted over (`forall (f : Type -> Type)`) but anonymous type constructors cannot be defined. This is the level of Haskell 98 and PureScript | Adding type-level functions moves the calculus to Fω. The same judgement as D6 |
| D2 | **Kinds and types are separate syntactic classes.** Dawn does not follow PureScript 0.14+ in unifying them | With no type-level functions the unification buys little, and separation avoids `Type : Type`. Kind checking terminates trivially and independently | Medium. The reflection API carries both a `Kind` and a `Type` |
| D3 | Kind polymorphism is **prenex only**. Kind schemes appear only on declarations — type constructors, data constructors, and top-level values. Neither types nor terms have kind quantifiers; instantiation is written explicitly at the use site as `T [[κ̄]]` or `M.x [[κ̄]]` | Preserves decidability while retaining higher-kinded types and the generality of `Row ε`. `Proxy : forall k. k -> Type` is prenex and therefore expressible. Rank-2 kinds such as `(forall k. k -> Type) -> Type`, and kind-polymorphic functions, are not | High |
| D24 | **Kinds are stratified into three layers**: row element kinds `ε ::= Type \| Effect`, general kinds `κ` (where `Row` takes only `ε`), and quantifiable kinds `q` (which exclude `Effect`). Every site that introduces a type variable, and every `[[κ̄]]`, requires `Γ ⊢ κ qkind`, and an arrow is quantifiable — and a type constructor declarable — only where it produces `Type` | Without the restriction, degenerate row kinds such as `Row (Type -> Type)`, which can have no elements, become well-formed, and `forall (e : Effect)` becomes derivable. `Effect` is needed as the result kind of effect constructors but must not be quantified. Higher-kinded types (`forall (f : Type -> Type)`) are unaffected. Confining row kinds to argument position is what keeps `nf` total on well-kinded rows: a type of kind `Row ε` is row syntax and nothing else | Low. Permitting quantification over `Effect` is also coherent, but then D16's restriction must be imposed separately |

## Rows

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D4 | Rows are **sharp**: no key occurs twice. Dawn does not adopt Leijen's scoped labels | Duplicate keys make `⊎` non-commutative and give the position of known fields relative to an unknown tail semantic weight, so no normal form exists without closing row variables. With sharp rows the normal form is a finite map from keys to payloads plus a set of row variables, and equality is fully decidable | Low. It propagates through the entire row theory |
| D16 | **Every row element has a key, and the key is one of four constructors**: `SymbolKey` for a written field or instance name, `TagKey` for a structural variant constructor, `PositionKey` for a tuple component, `EffectKey` for a declared effect. An effect element derives its key from the effect at the head of its payload unless a `SymbolKey` is written for it | Whether a key is written is not a concern of row theory, so one theory serves records, tuples, variants, and effects alike. What every key must be is **rigid** — independent of metavariable solving — for row equality to be decidable, which is what rules out using a payload type as the key. Deriving an effect's key keeps the common case free of ceremony; writing one is what lets a single effect appear twice in a row, which sharpness would otherwise forbid | Low |
| D5 | Structural relationships between rows are expressed by **erased constraints in the Core context**, `k ∉ ρ` and `ρ1 # ρ2`. They are not dictionaries | The row solver and the type class resolver are separate mechanisms. `#` carries no run-time content | Low |
| D6 | Core has exactly three row operators: `()`, `( ent \| ρ )`, and `ρ1 ⊎ ρ2`. **`Difference` and `Map` are not in Core** | Term-level `restrict` covers what `Difference` is needed for. `Map` requires type-level functions, whose termination is unsettled. Both can be added later as type-level functions over `Row ε`; admitting them now would make row equality undecidable | Medium |
| D13 | **Every structural key is a literal.** A `SymbolKey` and a `TagKey` are written in the source, and a `PositionKey` is what elaborating a tuple derives from where a component stands; none is a variable, and the kind grammar has no `Symbol` kind | This is not merely a simplification: it keeps row keys rigid, which is what makes row equality decidable, the same requirement as D16. The role a `Symbol` kind plays in PureScript — reflecting type-level labels to run-time strings — is served by `normalizeRow` in the elaborator. Note that the `Symbol` of `SymbolKey` is the written name itself, not a kind | Low. Introducing a `Symbol` kind requires re-validating row normalization and keeping key variables out of Core's row-extension position |

## Effects

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D7 | Function types **carry an effect row**: `τ1 -{ρ}-> τ2`. Dawn does not use an `Eff` monad | Making effects a type constructor splits function types into pure and effectful, and that split then appears at every FFI boundary and in every treatment of exceptions and asynchrony. Putting the row on the arrow makes purity the case where `ρ = ()` | Low |
| D8 | Effect containment is **not subtyping**. Widening is written explicitly as `openEff` | Core type checking then requires only syntactic equality. A secondary benefit is diagnostic precision: because rows do not widen silently, an unsatisfied obligation is reported at the function that failed to declare the effect | High. A decidable subsumption judgement on effect rows is available as a fallback |
| D15 | Handlers are **deep**: after a resumption, control is under the same handler | Standard, and the lowering is direct — a generator driver loop provides it. Shallow handlers can be built from deep ones. The number of resumptions is a separate decision, D18 | High |
| D18 | Core **does not restrict how many times a delimited continuation may be resumed**. The reference semantics is multi-shot. The v0.1 JavaScript and Wasm backends do not satisfy this: a second resumption raises a dedicated run-time error. This is an accepted, documented soundness gap that v1.0 must close | Continuations are ordinary function values, so multi-shot requires nothing extra; restricting it would require affine types in Core. The cost is backend-specific: one-shot is natural on JavaScript generators and on Wasm stack switching, while a native backend has no reason not to implement multi-shot | Medium. The Core decision is stable, but the v0.1 backends are non-conforming implementations |
| D20 | **`IO` is an ordinary monad, `IO : Type -> Type`, not an effect.** Every effect is interpreted into `()` or `IO`; an effect that is interpreted into neither is never executed. The entry point is `main : IO Unit` | `IO` alone admits no operation signature, so it is not an algebraic effect. As an effect constructor it would also introduce containment between effects — `Console` is a subset of `IO` — which sharp rows keyed by constructor cannot express. Removing it from the effect world dissolves the containment question and closes the question of what happens to uninterpreted effects. An effect whose *operation* takes an `IO` — a lift — subsumes other capabilities functionally, but it does so through an explicit handler and keeps its own key in the row, so no containment between effects arises and it is admitted ([Effects](05-Effects.md)). Preserving D7's granularity requires the standard library discipline of confining `IO` to interpreters and `main` in ordinary code | Low. It propagates through the standard library and runtime boundary |

## Terms and matching

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D9 | Pattern matching is represented in Core as a **decision tree with join points** | Makes the decision structure explicit and turns lowering to Mid IR join points into a structure-preserving translation | Low |
| D10 | A non-exhaustive match produces the **`Partial` effect**, surfacing partiality in the type. `fail` is derived notation for this, not a Core primitive | Gives the effect of PureScript's `Partial` class without a class mechanism or a dedicated language feature | Medium |
| D11 | **Core has no implicit arguments.** Elaboration turns them into ordinary arguments | After elaboration, a type class is nothing but dictionary passing | Low |
| D12 | **Core has no metavariables.** They exist only in Core⁺ | Keeps the trusted core small | Low |
| D14 | Recursive bindings must be **guarded**: each right-hand side is syntactically a function value | Under strict evaluation this rejects `letrec x = f x` at type-checking time rather than deferring it to an uninitialized reference at run time | High |
| D21 | An **operation signature is not a function type**; it is written `σ ->* τ`. Exactly one `->*` appears, at the same precedence as `->` and right-associative, on the spine. Everything to its left is an argument; what stands to its right is the type the continuation resumes with | In Dawn `->` asserts an empty effect row, so using it for an operation — the one thing that is by definition not pure — says the opposite of what is meant. The position of `->*` coincides with the arrow that carries the effect row in the generated function type, so currying and the purity of partial application follow from the existing rules. Multi-argument operations are expressible while Core operations remain single-argument | High. Surface syntax only |

## Modules, FFI, and surface syntax

| # | Decision | Rationale | Reversibility |
| --- | --- | --- | --- |
| D17 | Effect sequencing is **direct style**. `perform` is a Core construct and does not appear in surface syntax; operations are written as ordinary function calls and the elaborator emits `perform` | This is D7 seen from the surface. Requiring `do` and `bind` for effects would restore, at the level of syntax, the pure/effectful split that D7 removed from types. Coexistence with classical monads is unaffected, provided `bind` is effect-polymorphic. The spelling of `do` is left to a library syntax macro | Low. It moves with D7 |
| D19 | **Dawn uses FFI far more sparingly than PureScript**: leaf operations only, a small versioned ABI surface (D26), no dependence on representation, and per-backend implementations kept separate from declarations | Mid IR is designed not to leak representation to backends, and FFI is the only path around that. In PureScript, FFI code depends on the representation of values, which takes the choice of representation away from alternative backends and forces every library with FFI to be rewritten per backend. A small ABI surface does for backend independence what a small trusted core does for soundness | Low. It shapes the whole standard library |
| D23 | **Every arrow in a runtime-bearing position of a `foreign` type has an empty effect row.** Effects on the outside world are expressed by returning `IO` | `handle` intercepts only `perform`, while a `foreign` application calls the implementation directly. An effectful `foreign` would therefore let a handler remove the effect from the row while the actual effect bypasses the handler's clauses. On the argument side the same rule prevents the lowering's calling convention from leaking across the FFI boundary. It holds of the payload of a row element, which hands a value across as an argument does, and not of a constraint, which is erased and carries none. The condition is syntactically checkable | Low. It is inseparable from D20 |
| D22 | **Modules are namespaces.** Dawn has no ML-style module system: no functors, no sealing by signature, no first-class modules. Data abstraction is provided by export lists. Local open `M.( … )` is available, but declaring a dependency and introducing names into scope are separated, so dependencies remain determined by the module header | Core names are fully qualified and module boundaries disappear during name resolution. Functors would require Core to express functor application and signature matching, enlarging the trusted core by an order of magnitude. Header completeness is what makes incremental and parallel builds cheap | Low. Strengthening the module system requires returning to the Core design |
| D25 | **Executing an `IO` lies outside Core.** Core reduction halts at an `IO` value; execution is the responsibility of the runtime ABI, a separate normative specification covering `Base.IO.pure`, `Base.IO.bind`, native leaf actions, world state, and the invocation of `main` ([Semantics](08-Semantics.md)) | Keeps world state out of the trusted core and leaves Core's reduction a closed, deterministic system. What Core owes the ABI is narrow: D23 keeps effects out of the arrows of a `foreign` type, and the conformance condition on `δ_f` keeps them out of the implementation, so an `IO` value is inert until executed. The second half is an obligation on the backend rather than a consequence of D23. The cost is that the ABI must be specified before a program runs end to end | Medium. The boundary is the interface between the language and every backend |
| D26 | **`Base.*` is the versioned runtime ABI surface, and what a backend owes is graded by profile.** `Prim` holds what the rules of Core name, `Base.*` what a backend implements, `Prelude` the default portable environment, and portable libraries are written in Dawn over those. **Neither Core nor the ABI privileges a portable library**, whoever distributes it. `Base` is a prefix only the package implementing the ABI may claim, which package resolution verifies rather than the Core type checker, nothing in a Core module telling the ABI implementation of `Base.Int` from a forgery. The versioned ABI manifest defines the surface and the profiles over it, a backend manifest records which entries one backend implements, and target validation is where the two are compared; `Σ` records none of it | To the type checker a `Base` entry is an ordinary `foreign`, and its declared type is the same fact whichever backend compiles it, so `Σ` has nothing to add. A profile says what a backend is conformant *at*, which is more than the split between an entry whose absence leaves it unable to provide the standard runtime and one whose absence merely stops a program running. Naming the layer is also what makes the dependency legible: by D22 a module touching the ABI surface says so in its header, so portable code is distinguishable from code that is not. Fixing the direction of dependency is what the layering buys beyond a naming convention: `Prelude` owns the identity of the foundational types, so nothing it provides needs a library downstream of it | Medium. The layer is a naming and build-time discipline rather than a rule of Core, but where the boundary falls shapes the standard library |
| D27 | **`String` is a sequence of Unicode scalar values and `Char` is one of them.** Every `Base.String` entry presents that meaning whatever a backend holds in memory, and a Dawn `String` holds no unpaired surrogate. Operations counting UTF-16 code units or UTF-8 bytes live in the namespace of the target that has them — `Js.String`, `Wasm.String` — rather than in `Base.*` | Representation and meaning are separate concerns: a JavaScript backend may hold a JavaScript string and a Wasm backend UTF-8 bytes, and neither choice may reach a result. Were the meaning instead the target's own code unit, `length "😀"` would be 2 on JavaScript and 1 or 4 elsewhere — a difference in what a program computes rather than in how it is stored, reaching `switchLit`, equality, and every decomposition into `Char`. The cost falls where representation and meaning diverge, in how a JavaScript backend implements the string entries, and confining target-specific observation to a namespace the header names keeps that cost out of portable code | Low. It fixes what every backend presents and what the standard library may assume |
